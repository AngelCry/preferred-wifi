# AGENT_RULES.md — обязательные правила для агента

**Версия:** 1.3.1
**Дата:** 2026-11-24
**Основание:** аудит ветки `feature/wifi-database-room` (7 коммитов, red CI, неработающий код, регрессии, недостоверный отчёт); повторный аудит Phase A в `feature/wifi-database-room-v2` (4 отменённых прогона, 1 failure, Room-код из отклонённой ветки, `[x]` без CI, грязное дерево, ложный grep); серии коротких опросов CI вместо одного блокирующего ожидания (24 и 19 вызовов на один run).
**Статус:** обязательны к исполнению. Нарушение любого правила = шаг не принят, работа возвращается на доработку.
**Как пользоваться:** правила действуют на весь проект preferred-wifi. При каждом новом аудите я (ревьювер) дополняю и ужесточаю их; версия и changelog обновляются в конце файла.

---

## 0. Базовые принципы

0.1. **Отчёт — не доказательство.** Доказательство — это diff, реальный код, лог CI и артефакт сборки.
0.2. **Красная сборка останавливает всё.** Пока CI предыдущего шага не зелёный, новый функционал не добавляется и следующий шаг не начинается.
0.3. **Один шаг = одно логическое изменение.** Шаг должен быть объясним одним предложением и проверяем отдельно.
0.4. **Не ломать существующее.** Любое удаление кода, поведения, разрешения или подписки на событие — отдельное решение с обоснованием, а не побочный эффект рефакторинга.
0.5. **Не выдавать частичное за целое.** Формулировки «готово», «исправлено», «все замечания закрыты» запрещены, если хотя бы один критерий приёмки не выполнен.
0.6. **Сначала безопасность данных и работоспособность, потом архитектура.** Нельзя вести миграцию/БД/UI, пока базовый сценарий приложения сломан.
0.7. **Единственный источник требований — `preferred-wifi-roadmap-handoff-v2.md`.** Не вводить собственные приоритеты/этапы, противоречащие ему. Обязательный порядок: §3 (Shizuku/код-ревью) → §8 (текущий этап) → §4 (Room).
0.8. **План и правила меняет ревьювер, агент их только исполняет.** Если план обновлён на месте — перечитать изменённые разделы и синхронизировать копию в репозитории.

## 1. Определение готовности (Definition of Done)

Пункт считается выполненным только при одновременном выполнении всех условий:

1. Код компилируется: CI-run со статусом `completed` и `conclusion=success` именно для этого коммита.
2. Артефакт `preferred-wifi-debug` опубликован (шаг `Upload APK` не пропущен).
3. Критерии приёмки пункта выполнены и перечислены в отчёте.
4. Прогресс-файл обновлён честными статусами.
5. Diff не содержит удалённой функциональности без явного обоснования.
6. В отчёте есть commit hash, ссылка на run, ссылка на artifact.

Если условие 1 или 2 не выполнено — статус пункта максимум `[~]`, никогда `[x]`.

## 2. Дисциплина Git

2.1. Работать только в своей ветке, созданной от актуального `origin/feature/shizuku-auto-switch`. Ветку `main` не трогать.
2.2. Перед началом: `git fetch origin`, проверить базу, создать ветку, сразу выставить upstream (`git push -u origin <branch>`).
2.3. Не мержить в `main`, не удалять и не force-push-ить чужие/старые ветки. Сломанную ветку оставить как есть для аудита.
2.4. Один коммит = один шаг. Не допускается коммит, в котором одновременно: новая схема БД + миграция + UI + Gradle.
2.5. Обновление прогресс-файла входит в тот же коммит, что и сам шаг. Отдельные docs-only коммиты допустимы только для чисто документальных изменений.
2.6. Сообщение коммита должно соответствовать содержимому. `feat: complete ...`, меняющий только `.md`, запрещён.
2.7. Не пушить несколько коммитов подряд, пока не завершился CI предыдущего (см. п. 3). Один коммит = один пуш = один дождавшийся прогон; следующий коммит создаётся только после `completed/success` предыдущего.
2.8. Перед пушем: `git status`, `git diff`, отсутствие мусора/отладки/секретов, `git diff --check` (пробелы, маркеры конфликтов).
2.9. Не изменять `.github/workflows` и не заниматься секретами/сборкой `main` в feature-ветке.
2.10. Force-push допустим только для собственной feature-ветки после согласованного отката и только с `--force-with-lease`. После отката сначала дождаться зелёного run на восстановленном HEAD и только потом продолжать шаги.

## 3. CI — обязательный шлюз (критично)

3.1. После каждого шага — **один** пуш и **ожидание завершения** workflow.
3.2. Статус `cancelled` **не является** успехом. Отменённый прогон = шаг не проверен.
3.3. Из-за `concurrency: cancel-in-progress` быстрые пуши отменяют предыдущие сборки. Поэтому: пуш → дождаться финального статуса → только потом следующий коммит.
3.4. В отчёт включать: run ID, URL, commit hash, статус, статус шага `Build debug APK`, наличие артефакта.
3.5. Если сборка упала — исправлять **только этот шаг**, не добавлять новую функциональность. После двух неудачных попыток подряд — остановиться и доложить с полным текстом ошибки.
3.6. Нельзя заявлять «сборка должна пройти» или «workflow запустится автоматически» как результат. Результат — только фактический статус.
3.7. Успешный CI доказывает компиляцию, но **не** работоспособность на устройстве. Формулировки «работает на телефоне» без теста пользователя запрещены.
3.8. Локальная сборка не заменяет CI. Нельзя писать «CI verified green», если run не проверен. Противоречивые статусы в одном отчёте/прогрессе («CI verified» и «CI pending») запрещены: статус CI указывается только по фактическому run.
3.9. Любое утверждение о локальной сборке должно сопровождаться командой и её фактическим выводом. При красном CI локальная сборка не считается доказательством готовности шага.
3.10. Зелёный run действителен только для своего commit hash. Прогон на docs- или reset-коммите не подтверждает код-шаг; ссылка на чужой или более ранний run запрещена.
3.11. Отменённый прогон не «переиспользуется»: шаг остаётся `[~]`/`[ ]`, повторная проверка — новый пуш после исправления.
3.12. Ожидание CI — **одна блокирующая команда** (`gh run watch <id> --exit-status` либо PowerShell-цикл с `Start-Sleep`) с явным таймаутом инструмента не меньше 600000 мс. Максимум **две** проверки на один run. Запрещены серии коротких опросов (`github.actions_get` и подобные): каждый опрос — отдельный ход и простой. Если после двух проверок run не завершён — один отчёт «run <id> still running» и остановка, без статуса success.

## 4. Защита от регрессий (по факту аудита)

Перед изменением Activity/Service обязательно составить список существующего поведения и сохранить его:

4.1. Запрос runtime-разрешений (`ACCESS_FINE_LOCATION`, `NEARBY_WIFI_DEVICES`) — нельзя удалять или комментировать «временно».
4.2. Запрос `POST_NOTIFICATIONS` через Activity Result API — нельзя заменять комментарием «здесь нельзя запустить».
4.3. Регистрация/снятие слушателей Shizuku — парная: если `add...Listener`, то в `onDestroy` обязателен `remove...Listener`.
4.4. `onResume` должен обновлять состояние кнопок; удаление `onResume`/`onDestroy` без замены запрещено.
4.5. Отображение сетей из `scanResults` нельзя удалять, пока новый источник (Room) реально не наполняется и не наблюдается.
4.6. После правки — `git diff` по удалённым строкам: для каждого удалённого идентификатора ответить, где он теперь используется/заменён. Если ответа нет — вернуть.
4.7. `grep` по всем удалённым символам обязателен: не должно остаться вызовов несуществующих функций/полей (в прошлый раз так остались `checkPermissionsAndLoad()`, `shizukuPermissionListener` и др.).
4.8. Запрещено копировать/восстанавливать файлы из отклонённых веток (`feature/wifi-database-room`, audit-ветки) и из старого красного состояния. Единственный источник кода — база `origin/feature/shizuku-auto-switch` (для Phase A — `1b71355`).
4.9. `MainActivity` и сервисы правятся точечно от базы. Если diff файла заметно превышает объём шага или в нём появляются чужие классы/импорты — шаг останавливается и переделывается от базы, а не «дочинивается».

## 5. Компиляция, API и аннотации

5.1. Не выдумывать параметры аннотаций. Пример запрещённого: `@PrimaryKey(val = true)` — у Room `PrimaryKey` есть только `autoGenerate`.
5.2. Не использовать несуществующие API/классы. Примеры запрещённого: `android.content.ApplicationContext`, `kotlinx.coroutines.executor`, `ProcessLifecycleOwner.lifecycleObserver`.
5.3. Не добавлять зависимости без подключения плагина/репозитория. Пример: `kapt(...)` без `id("kotlin-kapt")` ломает конфигурацию Gradle.
5.4. Не тянуть `javax.*` (`javax.inject`, `javax.annotation`, `javax.sql`), если они не объявлены в зависимостях.
5.5. Перед использованием Android API проверять сигнатуру. Пример: `removeNetworkSuggestions` принимает `List<WifiNetworkSuggestion>`, а не массив строк.
5.6. Suspend-функции нельзя вызывать из не-suspend лямбд/колбэков. Для колбэков UI — `lifecycleScope.launch` с явной областью жизни.
5.7. Новые зависимости добавлять только при необходимости; фиксировать версию и причину.
5.8. Не оставлять неиспользуемые импорты, поля, заглушки. Заглушка (`isSaved() = false`) обязана быть помечена как «не реализовано», а не выдана за работу.
5.9. Перед каждым пушем обязателен гейт по запрещённым символам, вывод команды прикладывается в отчёт:
   `git grep -nE "androidx\.room|WifiNetworkDatabase|WifiNetwork\(|ProcessLifecycleOwner|lifecycleScope|kotlinx\.coroutines\.executor|dev\.rikka\.shizuku\.Shizuku|allowMainThreadQueries" -- app/src`
   Для Phase A вывод обязан быть пустым. Утверждение «grep пуст» без команды и вывода запрещено.
5.10. Room-код, Room-зависимости, `Entity`/`DAO`/`Database` запрещены до шага B1 — даже частично и «на будущее».

## 6. Room и работа с данными

6.1. Все обращения к DAO из UI — только `suspend` или `Flow`. Синхронные запросы DAO на главном потоке запрещены.
6.2. `allowMainThreadQueries()` запрещён как обходной путь.
6.3. `OnConflictStrategy.REPLACE` запрещён для объединения данных из двух источников: он затирает `preferred`, `saved`, `firstSeen`, `securityType`, `lastSeenInScan`.
6.4. Общий upsert обязан сохранять пользовательские и системные поля: `INSERT OR IGNORE` + частичный `UPDATE` в `@Transaction` либо явные `UPDATE`-запросы.
6.5. Переключение `preferred` обновляет только `preferred` и `lastUpdated`. Остальные поля не трогать.
6.6. `firstSeen` пишется один раз при создании записи и никогда не перезаписывается при обновлениях.
6.7. Миграция из SharedPreferences:
   - выполняется вне главного потока и в транзакции;
   - флаг `migration_done` ставится **после** успешного завершения;
   - SharedPreferences не очищаются;
   - при ошибке — не помечать миграцию выполненной.
6.8. Ошибка/частичное чтение системного списка не должны сбрасывать `saved` у остальных записей и не должны удалять локальные записи.
6.9. Сеть, исчезнувшая из сканирования или из системного списка, не удаляется из локальной БД автоматически.
6.10. В БД пишут оба источника (системный импорт и scan discovery) через один механизм; UI читает БД, а не `scanResults` напрямую.
6.11. Для сетей с одинаковым SSID схема должна допускать расширение (не зашивать SSID как единственный логический ID навсегда в API), но текущая реализация не должна ломать существующие записи.

## 7. Потоки и lifecycle

7.1. `HandlerThread` обязательно `start()` до получения `looper`; иначе `Handler(null)` → NPE. В прошлый раз это ломало foreground-сервис.
7.2. Binder IPC и любые блокирующие вызовы — вне главного потока; обновление UI/уведомлений — на главном.
7.3. Все созданные `HandlerThread`, `CoroutineScope`, ресиверы, слушатели должны корректно завершаться в `onDestroy`.
7.4. Scope корутин привязать к lifecycle (`lifecycleScope`, `viewModelScope`), а не создавать `CoroutineScope(...)` в `onCreate`.
7.5. Флаги состояния (например, `monitoring_active`) должны поддерживаться владельцем состояния: ставиться при старте, сбрасываться при остановке/`onDestroy` сервиса. UI не должен показывать состояние, которое не соответствует реальности.
7.6. Не использовать deprecated API без причины; если замена неполная (флаг только из UI), это фиксируется как ограничение.

## 8. UI и пользовательские строки

8.1. После изменения данных UI должен обновляться (Flow/`notifyDataSetChanged`), а не показывать устаревший снимок.
8.2. Набор preferred, переданный в адаптер, не должен быть «снимком навсегда»; при изменении — обновлять.
8.3. Не менять пользовательские строки и не вносить опечатки («наблюжение», «Предференции») побочно. Проверять diff строк.
8.4. Переключатели/кнопки должны отражать фактическое состояние после перезапуска/возврата в приложение.

## 9. Отчётность и файл прогресса

9.1. Статусы в прогрессе:
   - `[ ]` — не начато;
   - `[~]` — в работе / частично (с указанием, что именно не сделано);
   - `[x]` — выполнено по Definition of Done;
   - `[!]` — заблокировано (с причиной).
9.2. `[x]` запрещён, если нет зелёного CI и выполненных критериев приёмки.
9.3. Строка «Last updated» заполняется реальной датой. Шаблоны вида `{{timestamp}}` запрещены.
9.4. Нельзя писать «все N замечаний исправлены», если исправлены не все. Нужна таблица: замечание → что сделано → commit → run.
9.5. В отчёте обязательно разделять:
   - что сделано;
   - чем подтверждено;
   - что не сделано;
   - что требует проверки на устройстве.
9.6. Приоритеты и отклонения от порядка roadmap фиксировать в прогрессе с обоснованием.
9.7. Нельзя выдавать ранее существовавший код за исправление в этом шаге (проверять `git diff` базы).
9.8. Отчёт о шаге, меняющем состояние ветки (reset, force-push, создание/удаление ветки), обязан содержать фактический вывод git-команд: `git rev-parse HEAD`, `git status -sb`, `git log --oneline`, `git diff --stat` относительно базы.
9.9. Отчёт с грязным рабочим деревом (`git status --porcelain` непуст) недействителен: сначала коммит/очистка, затем отчёт.
9.10. Любая проверка в отчёте приводится командой и фактическим выводом (grep, `git diff --stat`, `git ls-tree`). Выдуманный или «ожидаемый» вывод = ложный отчёт.
9.11. Docs-коммит не переводит код-шаги в `[x]`. `[x]` ставится в шаге с зелёным run либо отдельным docs-коммитом со ссылкой на run каждого шага.

## 10. Чёрный список (повторение ошибок недопустимо)

- `[x]` без зелёной сборки.
- Пуш следующего коммита до завершения предыдущего CI.
- Удаление разрешений, слушателей, `onResume`/`onDestroy` как «побочный эффект».
- Вызовы удалённых функций/полей, оставшиеся после рефакторинга.
- `allowMainThreadQueries()`.
- `REPLACE` для объединения записей.
- Room-запрос на главном потоке.
- `HandlerThread` без `start()`.
- Заглушка, выданная за реализацию.
- Комментарий вместо рабочего кода («for now, directly toggle», «we can't launch in this context easily»).
- Docs-only коммит с сообщением о функционале.
- Формулировки «должно работать», «workflow запустится», «сборка пройдёт».
- Утверждения о работе на устройстве без теста пользователя.
- Копирование файлов/классов из отклонённой ветки или старого красного состояния.
- Room/`Entity`/`DAO`/зависимости до шага B1.
- `[x]` в docs-коммите без зелёного run соответствующего коммита.
- Отчёт при незакоммиченных изменениях.
- Выдуманный вывод grep/git как доказательство.
- Серия коротких опросов статуса CI вместо одной блокирующей команды.

## 11. Чек-лист перед отчётом (обязателен)

1. `git status` — чисто, ветка правильная.
2. `git log --oneline base..HEAD` — шаги соответствуют сообщениям.
3. `git diff base..HEAD` — просмотрены удалённые строки, регрессий нет.
4. `grep` по всем удалённым/переименованным идентификаторам — нет «висячих» ссылок.
5. CI-run для HEAD: `completed/success`, артефакт есть, ссылка сохранена.
6. Прогресс-файл: статусы честные, дата реальная, критерии приёмки записаны.
7. Все заявления отчёта подкреплены file:line / commit / run URL.
8. Нет неиспользуемых импортов, кода, зависимостей; нет секретов.
9. Пользовательские строки не изменены побочно; опечаток нет.
10. Разделы «не сделано» и «требует проверки на устройстве» заполнены.
11. `git status --porcelain` пуст; незакоммиченных правок нет.
12. Гейт по запрещённым символам выполнен, вывод пуст (для Phase A) и приложен к отчёту.
13. На каждый код-шаг есть свой run `completed/success` — не чужой, не отменённый и не docs-коммита.

## 13. Приложение A — известные ловушки проекта

| Ловушка | Правильно |
|---|---|
| `@PrimaryKey(val = true)` | `@PrimaryKey` у `ssid`, при необходимости `autoGenerate` |
| `android.content.ApplicationContext` | `android.content.Context` / `Context.applicationContext` |
| `kapt(...)` без плагина | подключить `id("org.jetbrains.kotlin.kapt")` (или KSP) |
| `ProcessLifecycleOwner.lifecycleObserver` | `ProcessLifecycleOwner.get().lifecycle.addObserver(...)`, зависимость `lifecycle-process` |
| `HandlerThread.looper` без `start()` | `thread.start()` до создания `Handler` |
| `removeNetworkSuggestions(arrayOf(ssid))` | `List<WifiNetworkSuggestion>` для старых SSID |
| `WifiNetwork(...)` без `securityType` | nullable-поле с default или явная передача |
| `getAllNetworks()` на main | `suspend`/`Flow`, вызов из `lifecycleScope` |
| `REPLACE` при scan/import | частичный `UPDATE` + `INSERT OR IGNORE` |
| `firstSeen = now` при toggle | обновлять только `preferred`/`lastUpdated` |
| Флаг миграции до завершения | ставить после успешной транзакции |
| `monitoring_active` только из UI | ставить/снимать сервисом, UI читает |
| Java-рефлексия hidden API | `runCatching`, конкретная ошибка пользователю |
| `main` — базовая версия без Shizuku | не ломать базовые сценарии; продвинутые функции только с Shizuku |
| Публичное чтение saved networks на Android 14 | Shizuku или честное ограничение, без заглушек |
| Самовольные приоритеты/этапы | следовать handoff v2: §3 → §8 → §4 |
| `import dev.rikka.shizuku.Shizuku` | `import rikka.shizuku.Shizuku` (зависимость `dev.rikka.shizuku:api`) |
| Копирование `MainActivity` из отклонённой ветки | точечные правки от базы, diff только по шагу |
| Room-код в Phase A | Room только с B1, вместе с плагином и зависимостями |
